# 架构说明

## 1. 数据流

```
                     ┌─────────────────────────────────────────────┐
   video_dir/*.mp4   │ 1. discover   models.discover()             │
        │            │    扫描目录、解析文件名中的日期、按时间排序    │
        ▼            └────────────────────┬────────────────────────┘
   VideoMeta                                │
   (path, title, recorded_on)               ▼
                     ┌─────────────────────────────────────────────┐
                     │ 2. transcribe  asr.transcribe()             │
                     │    ffmpeg 抽音频 → VAD 切段 → SenseVoice     │
                     └────────────────────┬────────────────────────┘
                                          ▼  transcript.txt
                                            [MM.SS] 文本
                     ┌─────────────────────────────────────────────┐
                     │ 3. note        note_writer.generate()       │
                     │    rules + schedule + transcript + 附件      │
                     │    → 模型 → 程序化校验（不过则定向重试）      │
                     └────────────────────┬────────────────────────┘
                                          ▼  *.课堂笔记.md
                     ┌─────────────────────────────────────────────┐
                     │ 4. render      md2docx.convert()            │
                     └────────────────────┬────────────────────────┘
                                          ▼  *.课堂笔记.docx
                     ┌─────────────────────────────────────────────┐
                     │ 5. deliver     notifier.push()              │
                     │    摘要程序化抽取 + 文件上传                  │
                     └─────────────────────────────────────────────┘
```

## 2. 为什么把「获取视频」排除在外

这条流水线的输入契约是**一个文件路径**，不是「一个平台上的一个回放」。

这样切分有三个实际好处：

1. **可测试。** 输入是本地文件，测试可以直接造 3 个假的 `.mp4`，
   不需要 mock 任何网络鉴权，也不需要账号。
2. **可替换。** 换一个视频来源只要往目录里放文件；换掉视频来源不影响这里任何一行。
3. **职责清晰。** 「怎么拿到视频」涉及与平台的关系、账号凭据、合规边界，
   它有自己的生命周期和风险，不该和「怎么把语音变成笔记」耦合在同一个仓库里。

因此 `vnotes` 里没有任何网络采集代码、没有平台专用的接口地址、没有账号令牌处理。
上游怎么得到视频是上游自己的事。

## 3. 状态机

五阶段，只进不退：

```
discovered ──► transcribed ──► noted ──► rendered ──► delivered
    │              │             │          │            │
    └─ ASR         └─ 模型        └─ docx    └─ 推送       └─ 终态
```

`state.json` 长这样：

```json
{
  "key": {"video": "/data/in/2026-09-01_课.mp4", "size": 3403223, "mtime": 1792984831},
  "stage": "transcribed",
  "attempts": {"asr": 1, "notes": 2},
  "failed_step": "notes",
  "last_error": "NoteGenError: 笔记校验未通过：…",
  "updated_at": "2026-09-01T22:31:04"
}
```

两个关键设计：

**幂等键是文件指纹，不是文件名。** `size + mtime` 变了就说明源文件被替换
（重新录制、换了导出版本），旧产物一律作废重来。否则重新导出的视频会静默复用旧笔记。

**失败不回退 `stage`。** 只写 `failed_step` / `last_error`。
这样笔记生成失败时，转写稿不会被视为「没做过」重跑一遍——
对一场两小时的直播，这是几十分钟的差别。

代价是：失败信息与阶段分开存，续跑的判断要同时看两者。
`Session.advance()` 在成功推进时会清掉失败字段，所以不会出现「已经是 transcribed 但还挂着 failed_asr」的矛盾状态。

## 4. 为什么不做多轮 agent

任务是确定性的文档转换：一份转写稿进去，一份结构化笔记出来。
没有外部工具要调，没有需要多轮试探才能确定的信息。

单轮生成 + 程序化校验 + 定向重试的失败模式是明确的：

- 模型返回的格式不对 → 校验器能具体说出哪条不对 → 带着这份清单重试一次
- 重试仍不对 → 抛错，让人介入

对比 ReAct 循环：多轮会引入「什么时候算完成」的判断问题，
成本和延迟都不可控，而这里并不需要搜索或计算能力。
规则足够复杂（日期识别、风险指数、排班对照）时，靠的是**规则写得清楚 + 校验写得严**，
不是靠多轮。

## 5. 校验器为什么值得写

模型会犯的错是**有规律的**，所以可以用代码拦：

| 校验项 | 拦住的真实失败模式 |
|---|---|
| 抬头讲师 ∈ 排班表 | 模型凭空编一个名字 |
| 日期 ↔ 星期相符 | 「2026-09-01（周三晚）」——9/1 是周二 |
| 讲师 ↔ 排班一致 | 日期对了但讲师写错（两位话术几乎一样，模型容易串） |
| 风险指数 ∈ 0–100 | `195/100` |
| 有免责声明 | 漏掉文末固定句 |

第三条尤其重要：这是**跨两个信息源的一致性检查**——
把「模型从内容里认出的日期」和「排班表」交叉验证，
单看任何一边都发现不了。

## 6. 摘要为什么不二次生成

推群摘要有四个字段：抬头、风险指数、一句话主旨、次日要点。

它们全部从笔记正文里**正则抽取**，不是让模型再写一遍。原因：

- 二次生成会引入新的幻觉，而这次没有校验器兜底（它面向人，不面向程序）
- 正文写「风险指数 62（高风险）」，摘要写「中风险」，读的人该信哪个？
  同一份产物内部矛盾，比稍微啰嗦的摘要严重得多

抽取逻辑本身也有边界情况（括号嵌套、超长截断、文末备注被误当主旨），
这些在 `tests/test_notifier.py` 里都有对应测试。

## 7. 依赖边界

```
config.py ◄── 所有模块
models.py ◄── pipeline, cli         （不依赖 asr / note_writer）
schedule.py ◄── note_writer, pipeline, cli
asr.py       外部依赖：ffmpeg, sherpa-onnx, onnx 模型
note_writer.py  外部依赖：openai 兼容 API
md2docx.py   外部依赖：python-docx
notifier.py  外部依赖：企微 webhook
pipeline.py  编排以上
cli.py       参数解析，不含业务逻辑
```

`models.py` 不 import `asr`/`note_writer`，所以状态机的测试可以在没有模型、
没有 ffmpeg 的机器上跑。这是 `tests/` 能在 2 秒内跑完的原因。
